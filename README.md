# Портфолио

Одностраничный сайт-портфолио с превью проектов. Чистые HTML/CSS/JS, без сборщика,
без внешних запросов (иконки — инлайн-SVG, шрифт заголовков лежит локально).
Открывается двойным кликом по `index.html`, работает и с `file://`, и с любого
статического хостинга.

Страница начинается с крупного заголовка-роли (`h1.lead__h`, заливка градиентом
из `--grad-head`), дальше сразу проекты: превью — главное, hero-блока нет.
Отдельной строки навигации в шапке тоже нет — меню по разделам сайта
(`#navMenu`) раскрывается кликом по имени с логотипом, там же подсвечивается
текущий раздел. Пункты меню набраны тем же шрифтом, что описания проектов
(`.card__d`): системное семейство, 16px, обычное начертание. Карточки идут друг
под другом во всю ширину: превью слева, текст справа. Уже 900px карточка
складывается в столбик. Резюме — в «Контактах».

## Структура

```
index.html                   разметка; контент подставляется из данных
assets/css/style.css         стили: тёмная тема по умолчанию + светлая
assets/js/app.js             рендер, меню, лайтбокс, тема, прогресс
assets/data/projects.js      ← ВЕСЬ КОНТЕНТ ПРАВИТСЯ ЗДЕСЬ
assets/fonts/handjet*.woff2  пиксельный шрифт заголовков (подмножества cyrillic/latin)
assets/fonts/handjet.css     @font-face к ним; cyrillic и latin вшиты как data: URI,
                             файл собирается tools/fonts.js — руками не править
assets/img/projects/*.jpg    превью проектов (1280×800)
assets/img/logo.png          логотип в шапке (144×144, из исходного PNG)
assets/img/og-v2.jpg        картинка для соцсетей (1200×630)
assets/img/favicon.svg       иконка
tools/shots.js               съёмка превью проектов с живых сайтов
tools/optimize.js            пережатие превью через canvas в Chrome
tools/og.html + tools/og.js  рендер og:image
tools/preview.js             съёмка превью самого сайта (dark / light / мобильный + крупные планы + демо-окно)
tools/smoke.js               смоук-тест вёрстки на jsdom
tools/verify.js              проверка в живом Chrome: клики, overflow, консоль
_preview/                    результат tools/preview.js (служебное, в .gitignore)
```

## Как менять контент

Всё в `assets/data/projects.js`:

- `window.SITE` — имя, роль, слоган, контакты, абзацы «О себе», факты, стек.
- `window.PROJECTS` — карточки. Поля: `title`, `kind`, `desc`, `tags`, `year`,
  `status` (`live` | `wip` | `archived`), `shot`, `shotPos`, 
  `links: { demo, demoLabel, demoIcon, web, repo }`.

**Превью — всегда 16:10, 1280×800.** В карточке кадр показывается в пропорции 16:10
(`object-fit: cover`), а в лайтбоксе — целиком (`contain`). Если положить картинку
другой пропорции, в лайтбоксе она будет отличаться по высоте от остальных, а в карточке
её обрежет по бокам. Кадр шире 16:10 обрезаем до 16:10 при подготовке, выбирая окно так,
чтобы важное в кадре осталось видимым.

Если обрезать нельзя и кадр всё же шире — есть необязательное поле `shotPos`
(значение как у `object-position`, например `'72% 50%'`): им сдвигается окно внутри
карточки. `0%` — левый край, `100%` — правый, по умолчанию центр. На лайтбокс не влияет.

Сейчас 6 проектов: пять игр/сайтов/расширений, последним — ORFree AI с превью
страницы RuStore. Порядок в массиве = порядок на странице.

`links.demo` — главная кнопка карточки, подпись по умолчанию «Открыть сайт»,
`demoLabel` её переопределяет, `demoIcon: 'store'` меняет иконку на магазин приложений.
`links.web` выводится рядом вторым каналом с подписью «Веб-версия».
Пустые ссылки не рендерятся, `shot: ''` даёт аккуратную заглушку с монограммой.

`links.demoEmbed: true` — клик по `demo` открывает демо не новой вкладкой, а в окне
монитора прямо на странице (см. следующий раздел). Ставится только тем адресам,
которые не запрещают показ в iframe. Сейчас это три игровых демо.

Чипов-фильтров рядом с проектами нет: убраны вместе с `#filters` / `.fbtn` / `.empty`.
Теги проекта остались только в данных и выводятся чипами внутри карточки — фильтровать
по ним нечем, поэтому `data-tags` в разметку не пишется.

Разметку и стили при правке контента трогать не нужно.

## Стиль кнопок

Кнопки в карточках, главная кнопка лайтбокса, кнопка переключения темы и ховер карточек
контактов — **строгие тёмные, без акцентной заливки и без акцентной рамки**. Выделение
главной кнопки держится только на плотности нейтральной рамки. Токены в `:root` /
`[data-theme="light"]`:

| токен | тёмная | светлая | назначение |
|---|---|---|---|
| `--btn` | `#06080b` | `#e7eaf0` | фон, темнее карточки |
| `--btn-hover` | `#12161e` | `#dbe0e9` | фон при наведении |
| `--btn-line` | белый 15 % | `#101828` 18 % | обычная рамка |
| `--btn-line-2` | белый 28 % | 34 % | главная кнопка, ховер |
| `--btn-line-3` | белый 42 % | 48 % | ховер главной кнопки |

Ориентир — токены shadcn/ui: в тёмной теме `--input` = `oklch(1 0 0 / 15%)`, `--border` = 10 %.
Своих «строгих тёмных кнопок» у shadcn нет — варианты либо светлее фона, либо белые,
а строгость создаёт именно рамка. Рамка в 7.5 % белого на почти чёрном фоне не читается,
поэтому ниже 15 % опускать не стоит.

Акцент (`--accent` / `--accent-2` / `--accent-3`) остался только в декоре: aurora-подсветка,
номер раздела `.sec__num`, свечение карточек при наведении, плюс `:focus-visible`
(это фокусная обводка для клавиатуры, её трогать нельзя).

## Шрифт заголовков

Заголовки и имя в шапке — Handjet. Подгруппы `cyrillic` и `latin` зашиты в
`assets/fonts/handjet.css` как `data:` URI и идут с `font-display: block`.

**Почему не файлом.** Пока шрифт лежит отдельным файлом, браузер узнаёт о нём
только после разбора CSS и первого расчёта раскладки, и запрос уходит в
низкоприоритетную очередь. Текст успевает отрисоваться системным шрифтом, а потом
подменяется; на задушенном канале окно подмены выходит под секунду — это и видно
как «сначала старый шрифт». `preload` лечит это по сети, но не по `file://`: там
`origin` = `null`, и `crossorigin`-preload шрифта падает в CORS с четырьмя ошибками
в консоли. Вшитые подгруппы опоздать не могут в принципе.

**Почему `block`, а не `swap`.** Разбор `@font-face` асинхронен даже для `data:`
URI, поэтому со `swap` браузер успевает нарисовать системный шрифт в первом кадре
и только потом подменить его. `block` не даёт нарисовать чужим шрифтом ни одного
кадра. Сдвига раскладки при этом нет: пока текст невидим, двигаться на экране
нечему.

Цена — вес CSS: 1.3 КБ → 18.2 КБ (base64 от 12.5 КБ шрифта). Стиль блокирует
отрисовку, так что килобайты на критическом пути, зато LCP от этого не страдает:
раньше системный шрифт рисовался рано, но подмена всё равно откладывала LCP до
прихода шрифта. Запросов стало на два меньше.

Подгруппы `cyrillic-ext` и `latin-ext` остались ссылками на файлы и `swap`: в
тексте сайта таких символов нет, браузер их не запрашивает, но если появятся —
отрисуются системным шрифтом, а не пропадут.

Проверок три. `smoke.js` смотрит на механизм: две вшитые подгруппы, у них `block`,
у ссылочных `swap`, `preload` шрифта нет. `verify.js` — что запроса на woff2 нет
вовсе и что под 400 мс задержки и 150 КБ/с подгруппы уже `loaded` к `DOMContentLoaded`.
`tools/fout.js` — пиксели: снимает полосу с заголовком кадр за кадром и сравнивает
маску глифов в первом кадре с финальной. По ширине заголовка подмену не увидеть:
при `block` раскладка считается по системному шрифту, и ширина «до» и «после»
совпадает. `INLINE_SUBSETS="" node tools/fonts.js` переключает на ссылки и валит
все три — так видно, что они не пустые.

## Демо в окне монитора

Клик по `Demo` у игры открывает `.demo`: рамка современного монитора, внутри стекла идёт
живая игра. Работает без правок в самих играх — они грузятся по своим адресам в iframe.

**Рамка нарисована на CSS, а не картинкой.** Первая версия была фотографией старого CRT
с прозрачным стеклом: красиво, но стекло занимало 21 % площади кадра, поэтому игра
получалась меньше окна вдвое, плюс 147 КБ ассета. У современного монитора рамка тонкая,
и всё это не нужно: `.demo__bezel` — это `padding: 11px 11px 26px` и градиент, подставка —
два псевдоэлемента с `clip-path`. Ассетов ноль.

**Потолок 720p — это не только вид.** Godot растягивает canvas по размеру окна, а окно
игры — это iframe. Значит, ограничив стекло, мы буквально уменьшаем число пикселей на
кадр: 1280×720 против 1920×1080 — вдвое меньше работы для GPU. Формула в `style.css`:

```css
width: min(1280px, 92vw, calc((100vh - 198px) * 16 / 9));
```

198px = 78 (полоса панели управления) + 16 (низ, чтобы не срезалась тень подставки)
+ 104 (рамка 11 + 26 + 2 и подставка 62). Верхняя полоса зарезервирована не зря:
без неё в низком окне кнопки «В новой вкладке» и крестик наезжают на угол корпуса.
Заодно стекло никогда не выше отведённого места, и монитор влезает целиком.
На 1600×1000 стекло выходит ровно 1280×720, в окне 1280×620 — 750×422.

Полоса задана как `padding` у `.demo`, поэтому `.demo__back` и `.demo__ui`
спозиционированы `fixed`, а не `absolute`: у absolute `inset: 0` считается от
padding-бокса родителя, и фон с панелью не закрыли бы зарезервированные полосы.

**Те же константы продублированы в `demoFits()` (`app.js`).** По ним решается, открывать
окно или увести ссылку в новую вкладку: если стекло вышло бы меньше 430 px, `demoEmbed`
не срабатывает и работает обычный переход (на телефоне играть в окошке 360 px нечего).
Меняешь формулу в CSS — поменяй и в `app.js`; расхождение поймает `verify.js`
(на 390 px окно не должно открываться, на 1600 px стекло обязано быть 16:9 и не шире 720p).

**Поведение окна.** Кадр создаётся заново на каждое открытие и удаляется при закрытии:
иначе игра продолжает крутиться в фоне и держит GPU с памятью. Фокус после `load` уезжает
внутрь кадра — управление работает без лишнего клика. Побочный эффект: **Escape действует,
пока фокус в самой странице; как только его забрала игра, выйти можно крестиком или
кликом по фону** — клавиши из чужого документа до родителя не доходят, это не лечится.
Если за 12 с кадр не поднялся, в стекле появляется ссылка на новую вкладку. Индикатор
на подбородке ждёт загрузку янтарным и зеленеет по `load` — то есть когда кадр реально
доехал, а не когда создан тег.

`allow="fullscreen; autoplay; gamepad; pointer-lock"`: захват мыши нужен двум играм
из трёх (`MOUSE_MODE_CAPTURED` у Bubble Peaks, `requestPointerLock` у LILCRAFT).
Лишние токены браузер игнорирует молча, поэтому набор выписан целиком.

**Тема.** Корпус красится токенами `--mon-*`: в тёмной теме почти чёрный, в светлой
серебристый — как техника в интерьере. Стекло в обеих темах чёрное.

Открыть окно можно и из лайтбокса — лайтбокс при этом остаётся открытым под ним,
прокрутка остаётся заблокированной до закрытия обоих.

Раньше здесь стоял корпус старого CRT (`old_pc.webp`, 1360×1156, стекло — прозрачная
дырка). Исходник лежит в `.workbuddy-ai/backup/old_pc.png`, если захочется вернуть:
WebP собирается из него одной строкой (`Image.open(...).save('old_pc.webp','WEBP',quality=85)`).

## Ловушки вёрстки, на которые уже наступали

- **`[hidden]` перебивается авторским `display`.** У `.btn` задан `display: inline-flex`,
  а авторское правило сильнее пользовательского `[hidden] { display: none }`, поэтому
  `el.hidden = true` ничего не скрывал. В начале `style.css` стоит
  `[hidden] { display: none !important; }` — не удалять.
- **Селектор по id проверяй по разметке.** `$('#hdr')` при `<header class="hdr" id="top">`
  молча возвращает `null`, и код внутри просто не выполняется.
- **`offsetParent` не годится для проверки видимости** внутри `position: fixed`:
  у детей он тоже `null`. Используем `getBoundingClientRect()` — см. `focusables()` в `app.js`.
- **Ссылка остаётся ссылкой.** У кнопки `Demo` и `href`, и `target="_blank"`, и обработчик
  клика с `preventDefault()`. Перехватываем только когда есть куда: иначе клик при
  отключённом JS, на узком окне или при `demoEmbed: false` работает как обычный переход.
- **Размер в CSS и размер в JS надо держать в одной руке.** Формула стекла живёт
  в `style.css`, а решение «открывать окно или увести в новую вкладку» — в `demoFits()`.
  Продублированные константы расходятся молча, поэтому расхождение ловит `verify.js`.
- **Удаление iframe рождает `requestfailed`.** Браузер рвёт незавершённые запросы
  удаляемого кадра, и сборщик ошибок в `verify.js` считает это поломкой сайта.
  Отсекаем по `ERR_ABORTED` — отмена не ошибка.

## Заметки по контенту

**PDF-резюме нет вообще** — ни файла, ни ссылки (`cv: ''`). Резюме живёт только на HH.
Исходный PDF на всякий случай отложен в `.workbuddy-ai/backup/` (служебная папка, в деплой
не идёт) — можно удалить. Вернуть кнопку = положить файл и прописать `cv: '<путь>'`,
скачивание в `app.js` уже обрабатывается.

Контакты идут в порядке Telegram → Почта → HH → GitHub (порядок задан в `renderContacts`).
Адрес почты лежит в `SITE.email` **без схемы**, `mailto:` собирается при рендере —
и ссылка намеренно без `target` и без `download`, иначе браузер предложил бы скачать
письмо файлом. Ссылка на HH заполнена; пустая строка убирает карточку из контактов.

Смоук-тест сверяет заголовки проектов с данными (`window.PROJECTS`), а не с литералами —
правки текста в `projects.js` его не ломают.

## Инструменты

Playwright берётся из пакета `@playwright/mcp`, браузер — установленный Google Chrome
(`channel: 'chrome'`). Свои браузеры не качаются, ничего не устанавливается глобально.

```bash
export PW_DIR="$APPDATA/npm/node_modules/@playwright/mcp"   # Git Bash
```

**Превью проектов** — `tools/shots.js`. Открывает живые сайты и снимает кадры.
Умеет дожидаться загрузки WebGL-сборок, жать клавиши и кликать по canvas
(кнопки внутри игры селектором не находятся), поворачивать камеру и идти вперёд.

```bash
node tools/shots.js              # снять всё
node tools/shots.js lilcraft     # снять только указанные проекты
```

Параметры съёмки — массив `SITES` в начале файла: `wait`, `keys`, `clicks`, `look`,
`walk`, `scroll`, `scrollTo` (абсолютная прокрутка), `clip` (снимок области),
`scale` (deviceScaleFactor), `hideSidebar` (спрятать правую колонку RuStore).

Кадр для ORFree AI снимается со страницы RuStore, а не с веб-версии: RuStore —
основной канал, так и подписано на карточке. Правую колонку RuStore прячем по
геометрии — классы там хешированные и меняются между сборками.

**Пережатие** — `tools/optimize.js`. Перезаписывает файлы на месте; откат — переснять
через `shots.js`.

```bash
node tools/optimize.js 1280 84           # ширина, качество — все файлы
node tools/optimize.js 1280 82 rustore   # только указанные slug'и
```

**og:image** — правится `tools/og.html`, рендерится в `assets/img/og-v2.jpg`.
Имя файла — это ключ кэша у мессенджеров: правишь картинку и хочешь, чтобы она
доехала до уже разосланных ссылок, — **меняй имя** (`og-v3.jpg` и т.д.) и путь
в `og:image` (он абсолютный, с домом прода). Один и тот же URL краулеры держат
в кэше месяцами и не перезапрашивают.

```bash
node tools/og.js
```

**Шрифт заголовков** — `tools/fonts.js`. Собирает `assets/fonts/handjet.css` из
woff2-файлов: подгруппы `cyrillic` и `latin` зашивает как `data:` URI, остальные
оставляет ссылками. `unicode-range` берёт из уже собранного файла, так что данные
Google Fonts в коде не дублируются.

```bash
node tools/fonts.js                 # собрать
INLINE_SUBSETS="" node tools/fonts.js   # вернуть ссылки на файлы (для проверки на подмену шрифта)
```

## Проверка

```bash
npm i jsdom
node tools/smoke.js    # рендер, меню, лайтбокс, контакты, дубли id, файлы — jsdom
node tools/verify.js   # то же в живом Chrome: клики, overflow, консоль, тема
node tools/preview.js  # картинки сайта в _preview/

# как в проде: тот же verify.js, но по HTTP, а не с диска
python -m http.server 8777
VERIFY_URL=http://127.0.0.1:8777/ node tools/verify.js

# подмена шрифта заголовков: кадр за кадром, пиксели
FOUT_URL=http://127.0.0.1:8777/ node tools/fout.js
```

**`file://` и HTTP — разные режимы.** По умолчанию `verify.js` проверяет с диска (быстро,
без сервера), но сайт живёт по HTTP. Отличия там, где они есть, вылезли бы только в проде,
поэтому хотя бы раз перед деплоем стоит прогнать с `VERIFY_URL`. Оба прогона дают
одинаковый результат — сайт не зависит от способа доставки.

Две проверки не дублируют друг друга. `smoke.js` — быстрый jsdom-прогон по структуре
DOM (~94 утверждения), без вёрстки. `verify.js` — настоящий Chrome: там ловятся
горизонтальный скролл на 390/1600 px, реальная загрузка превью и шрифта, включение
класса `is-stuck` у шапки при прокрутке, удержание фокуса внутри лайтбокса, ошибки
в консоли.

Демо-окно проверяется там же. Геометрия — из живого `getBoundingClientRect()`: стекло
обязано быть в пропорции 16:9 (иначе кадр игры обрезан или растянут), не шире 720p и
целиком влезать в окно вместе с рамкой и подставкой. Отдельный прогон на 1280×620 —
это тот случай, где формула и ломается: потолок 720p не работает, стекло обязано ужаться,
а монитор всё равно влезть. Дальше: игра реально поднялась внутри кадра (есть `canvas`),
индикатор позеленел, фокус уехал внутрь кадра, клик в центре стекла достаётся игре
(`elementFromPoint` → `IFRAME`), на 390 px окно не открывается вовсе, а путь «из лайтбокса»
не оставляет висящий `overflow`.

`verify.js` проверяет не только «что видно», но и «работает ли код»: именно эти
проверки выловили два дефекта, которые до того жили в проекте молча — шапка
не получала `is-stuck` (в `app.js` искали несуществующий `#hdr`), и `hidden`
не скрывал кнопку лайтбокса. **Нашёл подозрительное место — сначала напиши
падающую проверку, потом правь:** иначе не докажешь, что чинил что-то реальное.

**Оба теста сверяют контент с данными (`window.SITE` / `window.PROJECTS`), а не с
литералами.** Правки текста в `projects.js` тесты не роняют — только структуру.
В `smoke.js` из значений сверяются: роль в `h1`, число карточек, групп стека и чипов,
строки фактов, абзацы «О себе», имя, подписи кнопок, контакты и их порядок, ссылки
последней карточки. Литералами остались только структурные ожидания — 4 пункта меню,
один `h1`, отсутствие PDF. **Добавляешь проверку — бери значение из данных.**

Порядок контактов сверяется по хостам из `SITE` (`t.me | sekadist@gmail.com | hh.ru |
github.com`), а не по тексту: подпись может поменяться, порядок — нет. Почта —
единственный контакт без `target` и `download`: `mailto:` уходит почтовому клиенту,
а `download` превратил бы ссылку в скачивание пустого файла.

`verify.js` перед проверкой картинок прокручивает страницу: иначе `loading="lazy"`
превью ещё не запрашивались и проверка «загрузились» падает на ровном месте.

`smoke.js` грузит `index.html` в jsdom, подключает скрипты в том же порядке, что и HTML.
Отдельно ловит дубликаты `id` — на них уже ломался рендер стека (два элемента с
`id="stack"`, `querySelector` возвращал не тот); проверяет, что чипов-фильтров и пустого
состояния в разметке нет; дёргает меню — открытие кликом по имени, закрытие ссылкой,
кликом мимо и Escape; прогоняет лайтбокс — открытие, листание, закрытие, подпись кнопки;
прогоняет демо-окно — перехват клика по `Demo`, создание кадра, закрытие по Escape,
удаление кадра и то, что ссылка без `demoEmbed` осталась обычной. Выход 0 — всё зелёное.

`preview.js` перед `fullPage`-снимком прокручивает страницу: иначе `loading="lazy"`
картинки остаются пустыми на снимке. Снимок демо-окна он делает отдельно и ждёт не
только `canvas`, но и исчезновения `#status` из оболочки Godot: `canvas` появляется
сразу, движок стартует позже, и без этого в кадр попадала заставка «LOADING 1%».

`fout.js` — единственная проверка, которая смотрит на отрисованные пиксели, и
единственная, которой нужен HTTP: подмена шрифта видна только под задушенным каналом,
а `file://` сетью не душится. Кадры сравниваются по маске глифов (яркость выше порога),
а не по всем пикселям: под заголовком размытые пятна `.aurora`, и они перерисовываются
с чуть другим качеством — по полному кадру хеши не сходятся даже с одним шрифтом.
Толерантность 2 % от числа глифов, и перед выводами инструмент сам сверяет два кадра
с заведомо готовым шрифтом: если они расходятся, он честно говорит, что метод
нестабилен, вместо того чтобы врать про подмену.

## Деплой

Сайт статический, подойдёт любой хостинг.

```bash
git init
git add index.html assets tools .gitignore README.md
git commit -m "Portfolio: initial"
git remote add origin git@github.com:CityStas/<repo>.git
git push -u origin main
```

Для GitHub Pages: Settings → Pages → Source = `main` / root.
